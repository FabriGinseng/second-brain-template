# second-brain-template

Un kit di partenza per un "second brain" personale: un vault Obsidian di Markdown semplice, tenuto aggiornato da un agente di programmazione ([Claude Code](https://claude.com/claude-code)) secondo regole che controlli tu. Versione inglese: [README.md](README.md).

> **Stato: v0.1.** La struttura del vault, il wizard di installazione, i controlli e la dashboard locale funzionano. I job pianificati si generano per macOS, Linux e Windows. Usato ogni giorno su macOS. Su Linux e Windows i test automatici passano in CI, ma nessuno ha ancora usato davvero l'installer lì: vedi «Sistemi supportati». Niente di questo è stato provato con un account iCloud, Nextcloud o Fastmail vero.

> **Lingue.** La documentazione è bilingue: questo file in italiano, [README.md](README.md) in inglese. I file che il sistema scrive e legge (`STATE.md`, note del giorno, testi dei comandi, messaggi di `scripts/verify`) sono in italiano nella v0.1; gli ADR di partenza sono in inglese. Tradurli non è previsto per ora.

## Cosa ottieni

- **Progetti**: un breve `STATE.md` per progetto, riscritto (mai appeso), un `decisions.md` datato e una riga in `projects/INDEX.md`.
- **Regole che l'agente segue**: un `CLAUDE.md` corto, le decisioni in `docs/adr/` (note riservate, livello di autonomia), un glossario.
- **Regole applicate da un hook**: `.claude/hooks/regole.py` con l'elenco `regole.json` (ADR-012) chiede conferma per push, PR, deploy e `rm` e rifiuta force-push e riscrittura della storia, in ogni repo dopo `scripts/installa-regole.py` (il setup lo propone). `.claude/settings.json` protegge la cartella riservata.
- **Un ciclo di apprendimento** (ADR-015): un errore che qualcuno ha dovuto correggere lascia una riga datata in «Recurring errors» di `CLAUDE.md`; la seconda volta che torna la stessa causa diventa una regola, e una regola che si può verificare diventa un controllo. `/chiudi-giornata` propone la riga, `/weekly-review` propone la regola o il controllo, e niente si scrive senza un sì.
- **Un controllo**: `scripts/verify` verifica le regole del vault. Nessun modello, solo file.
- **Comandi e subagenti** in `.claude/`: vedi «Comandi». I testi dei comandi sono in italiano nella v0.1.
- **Una dashboard locale** (libreria standard di Python, solo `127.0.0.1`): progetti, piano, oggi, radar, servizi e limiti, post e un pannello dell'assistente. Mostra solo le pagine dei moduli che hai scelto.
- **`setup.py` e `doctor.py`**: un wizard di prima installazione fatto di moduli e un controllo di ciò che le tue scelte richiedono.

## Requisiti

- Python 3.9 o più recente e git.
- [Claude Code](https://code.claude.com/docs/en/setup) con un piano Claude a pagamento (il piano gratuito non lo include). L'agente, le bozze settimanali e la scelta del modello `claude` lo usano e consumano la quota del tuo piano.
- Facoltativi, solo se scegli la funzione che li richiede: [Ollama](https://ollama.com) per i modelli locali; Chrome, Chromium o Edge per le immagini dei post; [Obsidian](https://obsidian.md) per leggere le note con un'interfaccia comoda; n8n solo se lo preferisci al raccoglitore di novità incluso.

`python3 doctor.py` ti dice cosa manca e stampa il comando ufficiale di installazione per il tuo sistema. Non installa mai niente da solo.

## Installazione passo per passo

Gli stessi quattro passi su ogni sistema; cambiano i dettagli solo del primo.

1. **Installa Python, git e Claude Code.** Controlla con `python3 --version`, `git --version`, `claude --version` (su Windows `py -3 --version`).
2. **Prendi il template.** `git clone https://github.com/FabriGinseng/second-brain-template.git my-second-brain`, poi `cd my-second-brain`. Puoi aprire la cartella come vault in Obsidian.
3. **Lancia il wizard.** `python3 setup.py` (Windows: `py -3 setup.py`). Chiede la lingua, il tuo nome e ruolo, poi propone ogni modulo facoltativo con un sì o un no. Prima di scrivere qualcosa mostra un riepilogo e aspetta il tuo sì. Non sovrascrive mai un file che esiste.
4. **Controlla.** `python3 doctor.py`, poi `python3 scripts/verify`, che deve stampare `OK`.

Poi segui [INIZIA.md](INIZIA.md): circa 15 minuti, ogni passo dice cosa devi vedere.

### macOS

Python: `brew install python`, oppure l'installer di python.org (vedi la nota in «Se qualcosa non va»). git: `xcode-select --install`. Claude Code: `curl -fsSL https://claude.ai/install.sh | bash`. Qui funziona tutto ciò che descrive questa guida, compreso il calendario dall'app Calendario.

### Linux

Python e git dal gestore pacchetti (per esempio `sudo apt install python3 git`). Claude Code: lo stesso comando `curl` di sopra. I job pianificati usano i timer utente di systemd: lancia una volta `loginctl enable-linger $USER` perché girino anche quando non hai una sessione aperta. Per le immagini dei post installa Chromium o Chrome.

### Windows

Scrivi `py -3` dove questa guida dice `python3`. Python: `winget install Python.Python.3.12`. git: `winget install Git.Git`. Claude Code: `irm https://claude.ai/install.ps1 | iex` in PowerShell. Windows nativo è il percorso meno provato: WSL 2 è la scelta più sicura per Claude Code finché non sarà provato davvero.

## Il wizard e i suoi moduli

`python3 setup.py --list` mostra i moduli e cosa fa ciascuno; `python3 setup.py --add <modulo>` ne aggiunge uno dopo, senza toccare ciò che hai già. Un modulo può solo farti domande e poi fare poche cose fisse (scrivere un'impostazione, creare una cartella o un file che non esiste, aggiungere una riga a `.gitignore`, aggiungere regole `deny`). Non può eseguire comandi.

| Modulo | Cosa chiede | Cosa fa |
|---|---|---|
| `core` (sempre) | nome, ruolo, lingua | `config.json`, i file di `memory/`, il tuo nome in `CLAUDE.md` |
| `riservata` | il nome di una cartella riservata | la crea, la esclude da git, vieta a Claude Code di leggerla e modificarla |
| `radar` | temi, indirizzi dei feed, chi raccoglie le novità, quale modello per ogni passo | il radar del lunedì: novità dai tuoi feed, filtrate per i tuoi progetti, una breve scheda ciascuna in `radar/` |
| `bozze` | LinkedIn, Instagram o entrambi | le bozze del lunedì in `content/`; non pubblica mai |
| `servizi` | niente | la pagina Servizi della dashboard |
| `assistente` | quale modello risponde, quale calendario, e se gli appuntamenti possono andare a Claude | il pannello dell'assistente in «Oggi» |
| `scaffold` | niente | un registro dei template di progetto, due profili (`personal`, `lavoro`) e un promemoria per i repo che il vault non conosce: vedi «Traccia i repo che hai già» |

**Dopo le domande, il wizard prepara il computer.** Rileva RAM, disco libero, CPU e scheda grafica (solo questo, e non viene inviato da nessuna parte) e con quei dati propone un modello locale: con circa 8 GB di RAM uno da 4B, con 16 GB o più `qwen3:8b`, sotto Claude o nessun modello, e non offre scaricamenti se il disco è quasi pieno. Poi, un passo alla volta, chiede prima di fare ciascuna di queste cose e mostra il comando che lancerebbe: installare Ollama o Obsidian se hai scelto qualcosa che li richiede (con `brew` su macOS, `winget` su Windows, `flatpak` su Linux), scaricare i modelli locali scelti (`ollama pull`), attivare il controllo dei segreti prima dei commit, aggiungere la barra di stato dell'uso di Claude a `~/.claude/settings.json` (se ne tiene una copia), registrare i job pianificati e lanciare il radar una volta perché la sua pagina abbia qualcosa da mostrare. Puoi dire no a qualunque passo e farlo dopo a mano. **Non** esegue gli installatori che si scaricano da internet e si passano a una shell: per Claude Code (e per Ollama su Linux) stampa il comando ufficiale e lo lanci tu. Con `--yes` o `--answers` non installa mai niente.

Puoi anche lanciare il wizard senza domande: `python3 setup.py --answers answers.json --yes`. `tests/risposte-tutti.json` è un esempio completo. `python3 setup.py --dry-run` mostra cosa succederebbe e non cambia niente. `python3 setup.py --clean-example` toglie il progetto d'esempio quando hai i tuoi.

## In locale o con Claude: chi risponde a cosa

Ogni passo che ha bisogno di un modello ha la sua impostazione in `config.json` (`modelli`), e di fabbrica è `none`: nessun modello, niente esce dal tuo computer, niente da scaricare.

| Scelta | Cosa succede | Costo |
|---|---|---|
| `none` | il radar confronta parole chiave e leggi tu ogni candidata; il pannello dell'assistente resta spento | niente |
| `ollama:<modello>` | tutto resta sul tuo computer; più lento e meno preciso | spazio su disco e RAM |
| `claude` | più preciso; il testo di quel passo esce dal tuo computer verso Anthropic | la quota del tuo piano |

Cosa viene inviato con `claude`: per il radar, i titoli delle novità e lo stack e l'obiettivo dei tuoi progetti; per l'assistente, la tua domanda e, solo se l'hai permesso al setup, i titoli e gli orari dei tuoi appuntamenti. La cartella riservata non viene inviata da nessun passo. Date, giorni della settimana e ore libere le calcola il codice, non il modello, perché un modello sbaglia.

Con `radar_giudizio` a `claude` (o `claude:haiku`) il radar è un solo passo invece di due: ogni lunedì `scripts/radar.py` lancia `scripts/feed.py` (ogni novità ha un breve riassunto, e titolo e riassunto passano da `content-guard`) e poi `scripts/radar-claude.py`, una chiamata sull'inbox intera. Il modello risponde solo con il numero della voce e pochi campi brevi, che il codice controlla: titolo e link della scheda sono sempre quelli dell'inbox. Una scheda (al massimo 8 a settimana) dice i progetti, il tipo (`progetto`, `skill`, `sicurezza`), cos'è, cosa farci e quanto costa provarla. La dashboard mostra la scheda e permette di votarla Utile o Non utile (`radar/feedback.jsonl`), e `/morning` elenca le schede nel brief. Con un modello locale restano i due stadi. Se le novità le raccoglie n8n, `feed.py` non parte da solo. Buoni feed per chi sviluppa: le release dei propri pacchetti (`https://github.com/<owner>/<repo>/releases.atom`), `https://nodejs.org/en/feed/vulnerability.xml` e `https://github.com/anthropics/claude-code/releases.atom`.

`python3 scripts/modello.py --ram` suggerisce un modello locale per la tua RAM (circa 8 GB: un modello da 4B; 16 GB o più: `qwen3:8b`). Sono soglie, non misure sul tuo computer. `python3 scripts/modello.py --check-model <passo>` lancia tre richieste di prova fisse e ti dice se il modello scelto è adatto. Per scaricare un modello: `ollama pull <modello>`.

## L'assistente e il tuo calendario

Il pannello in «Oggi» risponde a domande sulla tua giornata («cosa scade questa settimana?», «quando sono libero domani?») e può proporre un appuntamento che confermi con un clic. Non ha strumenti né web: vede solo un testo che prepara il codice. Il modello può sbagliare, e la pagina lo dice.

Il calendario passa da `scripts/calendario.py`. Scegli un provider in `config.json` (`calendario.provider`) o nel wizard:

| Provider | Sistemi | Legge | Scrive | Serve |
|---|---|---|---|---|
| `macos` | macOS | sì | sì | l'app Calendario (con gli account Google e iCloud già dentro) |
| `ics` | tutti | sì (anche gli eventi ripetuti) | no | l'indirizzo iCal segreto di un calendario, o un file `.ics` |
| `caldav` | tutti | sì | sì | server, utente e una password per app (iCloud, Nextcloud, Fastmail) |
| `none` | tutti | no | no | niente: l'assistente dice che non conosce i tuoi appuntamenti |

Gli indirizzi e le password sono credenziali. Stanno **fuori** dal vault, che finisce in git: in `~/.config/second-brain/` su macOS e Linux, in `%APPDATA%\second-brain\` su Windows, in file leggibili solo da te (`chmod 600`; altrimenti il provider rifiuta di leggerli).

- `calendari.json` per `ics`: `{"calendari": [{"nome": "Personale", "url": "https://..."}, {"nome": "Festività", "file": "/percorso/festivita.ics"}]}`. In Google Calendar l'indirizzo sta nelle impostazioni del calendario, «Indirizzo segreto in formato iCal». Si accettano solo indirizzi `https://`.
- `caldav.json` per `caldav`: `{"server": "https://caldav.icloud.com", "utente": "tu@example.com", "password": "password per app"}`. Solo `https://`, i reindirizzamenti non si seguono, un server che indica un altro dominio è rifiutato e nessun messaggio d'errore mostra la password.

Se un calendario non si legge, l'assistente non risponde sulle ore libere, invece di dirti che sei libero quando non lo sei. Se il modello è `claude` e non l'hai permesso al setup (`moduli.assistente.calendario_al_cloud`), l'assistente non riceve i tuoi appuntamenti. Scrivere su Google Calendar fuori dal Mac non è supportato; la lettura funziona con l'indirizzo iCal segreto. Le regole di ripetizione che il lettore non capisce (per esempio «secondo martedì e quarto giovedì») compaiono come avviso in «Oggi», non sono ignorate in silenzio.

## La dashboard

`python3 scripts/dashboard/server.py`, poi apri http://127.0.0.1:8765. Ascolta solo sul tuo computer. Il menu mostra le pagine dei moduli che hai scelto; una pagina che non hai scelto non c'è. `second-brain.dashboard` (vedi «Job pianificati») la tiene in esecuzione: se si ferma, anche senza errori, riparte da sola (KeepAlive di launchd, `Restart=always` di systemd, su Windows un controllo ogni 10 minuti). Su Linux e Windows i pulsanti con lo stato dei job restano vuoti perché usano launchd.

**La mappa.** Ogni progetto e argomento è un nodo; i suoi task di `docs/piano.md` gli stanno attorno quando ci passi sopra o lo selezioni. Un task ha uno di quattro stati, letto dalle sue dipendenze (`id:`, `dopo:`, `chi:te`): **pronto** (grigio pieno: non aspetta più nulla), **in corso** (ambra), **in attesa** (grigio tratteggiato e sottile: un task da cui dipende non è ancora `[x]`) e **fatto** (verde). L'anello attorno al nodo ha un segmento per stato, l'attesa è tratteggiata così non si legge solo dal colore, e il numero al centro conta i task pronti; il suggerimento del nodo e il pannello dicono «N pronti · M in corso · K in attesa». Il pannello raggruppa i task del nodo in «Pronti da avviare», «In corso», «In attesa» e «Fatti» (chiusi). Una riga in attesa dice cosa aspetta («aspetta: <task>», con il nodo se è un altro, oppure «aspetta: te — <task>» se è un tuo compito); un `dopo:` rotto o un ciclo mostrano «riferimento rotto: <id>» o «ciclo di dipendenze». Selezionando un task in attesa compare il filo di dipendenza: una freccia da ogni altro nodo da cui dipende e il punto evidenziato per un bloccante nello stesso nodo, un task alla volta. Sotto i 760 px la mappa diventa un elenco con gli stessi stati, gruppi e motivi. «Avvia in Claude» compare solo sui task pronti o in corso: il server rifiuta (HTTP 409) un task che aspetta, che ha un errore nelle dipendenze o che è tuo (`chi:te`, con l'etichetta «Tocca a te»). La spunta a mano resta sempre libera. Claude si apre nel repo del task: quello del suo marcatore `repo:`, oppure l'unico repo del progetto. Se c'è più di un repo tra cui scegliere, il server risponde 409 e chiede la scelta («Scegli il repo in cui avviare.»); il nome che torna si accetta solo se è uno di quei repo, mai letto come un percorso. Un repo elencato la cui cartella manca è rifiutato, non sostituito dal vault, che resta la cartella di un progetto senza repo. In un progetto in cui due righe `Repo` hanno lo stesso nome di cartella si avvia solo un task il cui `repo:` nomina uno degli altri repo; ogni altro task è rifiutato, qualunque repo tu scelga, e il suo dialogo di «Avvia» lo dice invece di offrire una scelta: «Due repo di questo progetto hanno lo stesso nome (<nomi>): rinomina una delle cartelle o togli una riga Repo dallo STATE.», con «Avvia» spento. Alla mappa arrivano solo i nomi gemelli (`repoDoppi`), mai i loro percorsi. Claude non parte mai nella radice di un disco, dentro la cartella del lavoro o `_private` di `projects/` o la cartella riservata scelta al setup, ovunque stia nel vault (anche attraverso un link e, se una di queste cartelle è a sua volta un link o una junction, nella cartella a cui porta), né in una cartella che ne contiene una, tranne la radice del vault: quelle note non vanno mai a un modello cloud ([ADR-002](docs/adr/ADR-002-confidential-notes.md)). Un repo su una condivisione di rete (`\\server\share` o, su Windows, una lettera di unità collegata a una condivisione) è rifiutato prima di toccarlo, e quando `config.json` esiste ma non si legge, ha una forma inattesa, accende il modulo `riservata` senza una cartella o nomina una cartella che il setup rifiuterebbe, la cartella riservata non si conosce, quindi nessun task si avvia finché non lo correggi («config.json non leggibile o non valido: l'avvio è sospeso finché non lo correggi.»; la mappa si carica lo stesso). La cartella riservata si riconosce con qualunque maiuscola e separatore: `Projects/Secret` o `projects\Secret` è la cartella `projects/secret`, e una riga di `INDEX.md` con quel nome vale come un progetto del lavoro (il suo STATE non si legge, i suoi task non si avviano). Un repo così è rifiutato («Cartella non valida per questo task.») e Claude si apre nella cartella che il controllo ha approvato, con i link risolti. Un nodo con più di un repo ne mostra i nomi sotto il tipo (tre al massimo, poi «+k»; l'elenco intero sta nel suggerimento del nodo e di quella riga). Ogni riga di task ha un'etichetta per ogni suo repo valido e «repo sconosciuto: <nome>» per un `repo:` che il progetto non ha; un task pronto che condivide un repo con un task in corso dello stesso nodo porta la scritta «stesso repo di un task in corso», un avviso e non un blocco. Un nome di repo più lungo di 24 caratteri si taglia con «…» sull'etichetta e sul pulsante del filtro; il nome intero sta nel suggerimento ed è quello che leggono i lettori di schermo. Nel pannello di un nodo con più di un repo, sopra i task, il filtro «tutti / <repo>…» mostra i task che toccano quel repo più quelli senza un repo valido, e chi non ha `repo:` è segnato «repo non indicato». Il dialogo di «Avvia» dice «Repo: <nome>» quando il repo è uno solo; quando sono di più mostra una scelta con i soli nomi, nessuno selezionato, e «Avvia» resta spento finché non scegli. I candidati sono i `repo:` validi del task se ne ha più d'uno, altrimenti tutti i repo del progetto; se il piano è cambiato e il server chiede comunque la scelta, il dialogo si riapre con i repo tra cui scegliere. Un clic su un nodo, o Invio o Spazio, lo seleziona e la mappa scorre (circa 0,3 s; un salto quando il sistema chiede movimento ridotto) fino a inquadrare il nodo e i suoi task; un clic sullo sfondo, Esc o «Torna alla prossima azione» la riportano alla vista di prima, e la rotella, un trascinamento, un pizzico o «Adatta» fermano lo scorrimento dov'è. Sotto i 760 px non c'è zoom: si vede l'elenco. Il resto del movimento segue solo quello che fai, dura al massimo 0,3 s ed è spento quando il sistema chiede movimento ridotto: i task di un nodo si aprono a ventaglio quando il puntatore lo apre (mai quando ti sposti con Tab), il nodo selezionato tiene un anello grigio, il pannello sfuma sul contenuto nuovo, il filo delle dipendenze si disegna, e gli obiettivi che una pastiglia mostra o nasconde compaiono e spariscono in dissolvenza. Caricare o aggiornare la mappa non anima mai nulla. Ogni nodo che può ricevere un task (un nodo con una cartella e un nome che è un tag valido) ha un «+» in alto a destra del disco per aggiungerne uno, qualunque cosa contenga già. Nel pannello un titolo di task lungo va a capo da solo e la data e i segni gli vanno sotto.

**Obiettivi sulla mappa.** Un task con `obiettivo:<slug>` in `docs/piano.md` appartiene a un obiettivo; gli obiettivi stanno in `docs/obiettivi.md`. Gli obiettivi stanno in una fascia sopra i nodi, come rettangoli arrotondati, con linee leggere tratteggiate verso i nodi che toccano. Ogni rettangolo mostra il titolo e una barra con un segmento per stato, nell'ordine fatti, in corso, pronti e in attesa (tratteggiato, come nell'anello), e sotto «N di M fatti», e la ripartizione completa sta nel suggerimento e nell'etichetta per i lettori di schermo, «<titolo>, obiettivo: N pronti · M in corso · K in attesa · F fatti». Un obiettivo usato nel piano ma assente da `docs/obiettivi.md` compare comunque, con lo slug come titolo, il contorno tratteggiato e «non definito»; un obiettivo definito senza task mostra la barra vuota e «nessun passo». Il filtro «Obiettivi» mostra gli obiettivi e i soli nodi che toccano («Tutto» e «Aperti» mostrano anche gli obiettivi, «Progetti» e «Argomenti» no). Una riga di task con `obiettivo:`, nel pannello di un nodo e nell'elenco, ha un piccolo pulsante «obiettivo: <titolo>» (il titolo tagliato a 24 caratteri, intero nel suggerimento): un clic, o Invio o Spazio, seleziona quell'obiettivo, lo mostra nella fascia anche se una pastiglia lo aveva ripiegato e apre il suo pannello; con «Progetti» o «Argomenti», che non disegnano obiettivi, prima riporta la mappa su «Tutto». Selezionando un obiettivo (un clic sul suo rettangolo lo apre come grafo, vedi sotto) le sue linee diventano piene, gli altri nodi si attenuano e si apre il suo pannello: il titolo, «obiettivo · <progetti>», i conteggi, «Aggiungilo in docs/obiettivi.md» se non è definito, e i suoi task di tutti i progetti negli stessi gruppi di un nodo, ognuno con l'etichetta del suo nodo, oppure «Nessun passo nel piano con questo obiettivo.» se non ne ha. Lì «Avvia» lancia Claude nel repo del task, scelto con la stessa regola e lo stesso dialogo del pannello del suo nodo. Sotto i 760 px l'elenco mostra gli obiettivi prima dei nodi, ognuno con i suoi task aperti raggruppati per passo come nel grafo qui sotto («Passo 1 — in parallelo: 3 task»), i fatti ripiegati in fondo. Un obiettivo non è mai un nodo: può avere lo stesso nome di un progetto senza confondersi, e non cambia i conteggi in alto né i task di ciascun nodo.

**Scadenze sulla mappa.** Un obiettivo con `scadenza:` in `docs/obiettivi.md` mostra «scade <giorno>» su una riga sua sotto la barra. Un obiettivo è «a rischio» quando gli servono più giorni lavorativi di quelli che restano prima della scadenza, oppure quando ha task aperti a scadenza passata: il rettangolo porta «a rischio» in grassetto accanto alla data e un contorno d'avviso; a scadenza passata dice invece «scaduto», con il contorno rosso. Quando la data e la parola non stanno nella larghezza del rettangolo (una mappa stretta, un carattere più grande), la parola va su una riga sua e quel rettangolo cresce di una riga. Lo stato è sempre una parola, mai solo un colore, e sta anche nel suggerimento e nell'etichetta per i lettori di schermo. Il pannello dell'obiettivo comincia con la scadenza e la stessa parola, «servono N giorni, ne restano M» (giorni lavorativi, oggi e la scadenza compresi), la frase «Le date ipotizzano che i task indipendenti procedano in parallelo.» e il file del piano dell'obiettivo (`piano:`) come semplice testo. Una riga di task, nel pannello e nell'elenco, mostra «entro il <giorno>» quando la sua data è calcolata, in rosso e preceduta da «in ritardo» quando un task pronto l'ha superata, e «senza stima» quando non ha `stima:` e quindi conta zero ore; una data scritta a mano in testa alla riga vince e si vede come prima. Un obiettivo senza scadenza non mostra date né rischio. La fascia resta corta: gli obiettivi con tutti i task fatti si raccolgono in una sola pastiglia «+k completati», e oltre due righe di obiettivi aperti gli altri finiscono dietro «+k altri». Ogni pastiglia è un pulsante (Invio o Spazio) che mostra i suoi obiettivi e, premuta di nuovo, li richiude; i nodi si dispongono sotto le righe davvero disegnate. Un obiettivo selezionato non viene mai nascosto. Sotto i 760 px l'elenco mostra tutti gli obiettivi, con scadenza e stato.

**Un obiettivo come grafo.** Un clic su un rettangolo della fascia degli obiettivi (o Invio o Spazio) apre l'obiettivo come grafo sopra la mappa, dall'alto in basso. In cima c'è l'obiettivo, con i conteggi, la scadenza e «a rischio» se lo è. Sotto, i suoi task in righe per dipendenza: la prima riga è ciò che non aspetta niente di mostrato, ogni riga dopo ciò che aspetta al massimo la riga sopra, quindi i task di una stessa riga possono procedere in parallelo. Una riga troppo larga per la mappa va a capo su più linee, tenute insieme da una parentesi «in parallelo» a sinistra. Le frecce vanno dal task che blocca a quello che aspetta; linee leggere uniscono l'obiettivo alla prima linea della prima riga. Ogni rettangolo mostra il titolo su due righe (un prefisso «Titolo · » che più task del piano hanno in comune lì si toglie, il titolo intero sta nel suggerimento e nell'etichetta per i lettori di schermo), poi stato, stima e progetto, e su una terza riga «in ritardo», «stesso repo di un task in corso» o «tocca a te» quando valgono; in attesa è un rettangolo tratteggiato, un errore un rettangolo rosso con la parola «errore». Un task di un altro obiettivo, o di nessuno, che uno dei nostri aspetta, o che aspetta uno dei nostri, compare come rettangolo «fantasma» punteggiato con «altro obiettivo» o «senza obiettivo», nella riga sopra chi lo aspetta o sotto chi lo blocca; un fantasma non si espande oltre, e premerlo apre il grafo del suo obiettivo, o il suo task nel suo nodo se non ha obiettivo. Un ciclo non rompe mai il disegno: ciò che lascia senza ordine va in un'ultima riga, «fuori ordine: dipendenze in ciclo», in rosso. I task fatti sono nascosti, perché i loro legami sono soddisfatti: «Mostra fatti (n)» nell'intestazione li mostra, attenuati, e le righe si ricalcolano con loro. Un clic su un rettangolo, o Invio o Spazio, seleziona quel task nel pannello dell'obiettivo (pulsanti di stato, «Avvia») e lo evidenzia con chi lo blocca e i task che sblocca. Ogni rettangolo si raggiunge con Tab, riga per riga, e la sua etichetta dice stato, progetto, passo e «aspetta: …» / «sblocca: …». «Mappa» nell'intestazione, Esc o un clic sul rettangolo dell'obiettivo in cima chiude il grafo e ridà la mappa con la sua vista e il suo zoom; un aggiornamento dei dati tiene aperti il grafo e la selezione finché l'obiettivo esiste. Un grafo lungo scorre dentro la mappa. Sotto i 760 px il grafo non c'è: l'elenco raggruppa i task dell'obiettivo per gli stessi passi.

**Harness dalla mappa.** Con l'harness acceso in `config.json` (`moduli.harness.attivo`), ogni progetto con un repo mostra a che punto è: `da decidere`, `escluso`, `da valutare`, `da rifare`, `da adeguare` o `conforme`, con i numeri e la data dell'ultimo report. Due pulsanti scrivono la decisione nello `STATE.md` del progetto: «Adegua all'harness» e «Non adeguare questo progetto». Il primo segna solo la decisione e ti dice il comando da lanciare nel repo (`/ai-native-harness:audit`); dalla dashboard non parte nulla, perché un audit esegue i check del progetto. I progetti con un repo e senza una decisione restano elencati sotto «Harness da decidere», e il loro nodo ha il contorno tratteggiato, finché non rispondi: un silenzio non vale come un no. «Nuovo progetto» fa la stessa domanda quando indichi un repo, e la fanno anche `/nuovo-progetto` e `/adotta-repo`. Con l'harness spento non compare nulla di tutto questo.

**Progetti dalla mappa.** «Nuovo progetto» sulla mappa crea `projects/<nome>/STATE.md` dal template e la riga in `projects/INDEX.md`, come `/nuovo-progetto`: il nome e, se vuoi, la cartella del repo, lo stack e la priorità. Con un progetto selezionato, tre pulsanti ne impostano la priorità (alta, media, bassa) nella riga dell'indice. Nessuno dei due tocca i progetti di lavoro o la cartella riservata. Un progetto il cui STATE non nomina una cartella (nessuna riga `Repo`, oppure solo `nessuno` o il segnaposto del template) ha «Imposta cartella» in fondo al pannello: scrivi il percorso assoluto di un repo git su questo computer, e lo si controlla come il repo di un progetto nuovo (i percorsi di rete sono rifiutati prima di toccare il disco, e così le cartelle del lavoro e riservata, la radice di un disco, una cartella che ne contiene una e qualunque cosa dentro `projects/` del vault). Lo STATE prende `- **Repo:** <percorso>` al posto della riga vuota, con la data di oggi, e così la data della sua riga nell'indice; da lì «Avvia» si apre in quella cartella. Un errore dice cosa non va e non ripete mai il percorso. Con il modulo dell'harness acceso, il progetto poi aspetta in «Harness da decidere». Per cambiare un repo già impostato modifica il suo STATE. «Archivia progetto», in fondo al pannello di un progetto, lo archivia dopo un dialogo che lo nomina e dice cosa succede: la sua riga esce da `projects/INDEX.md` e la sua cartella va in `projects/_archivio/<nome>` (`<nome>-AAAA-MM-GG`, poi `-AAAA-MM-GG-2`…, se è già presa: non si sovrascrive mai nulla). È un cambio di nome dentro `projects/`: nessun repo sul disco viene toccato, una cartella del progetto (o `projects/_archivio`) che è un link o una junction è rifiutata, e così una che è, contiene o sta dentro la cartella riservata (o dove porta, se è un link), e con `config.json` illeggibile non si sposta nulla. Le sue righe `#<nome>` restano in `docs/piano.md` e ricompaiono come nodo argomento, dove «Avvia» apre il vault. Per ripristinarlo rimetti la cartella in `projects/<nome>` e la sua riga in `projects/INDEX.md` (la data in fondo alla riga deve essere quella della riga `Aggiornato` del suo STATE), poi lancia `scripts/verify`.

**Icona nella barra** (`second-brain.tray`, Windows e macOS, parte al login): un pallino nell'area di notifica (Windows) o nella barra dei menu (macOS), verde quando la dashboard risponde e rosso quando no (controllo ogni 30 secondi). Il menu ha tre parti. **Dashboard**: aprila, avviala o riavviala (su Windows prima ferma un `server.py` di questo vault rimasto in ascolto sulla porta 8765; un altro programma su quella porta non viene mai fermato, e un avviso lo indica), fermala (su Windows il controllo ogni 10 minuti la fa ripartire; su macOS resta ferma finché non la avvii o rientri). **Avvia job**: lancia subito `morning`, `feed + radar` (radar parte quando feed ha finito), `chiusura`, `bozze` o `pulizia`; un job non registrato non compare. **Notifiche**: un avviso quando la dashboard cade o torna e quando un job finisce con un errore (una volta per esecuzione), con un interruttore che le spegne finché non chiudi l'icona. **Esci** chiude solo l'icona. Solo codice nativo: `scripts/tray/tray.ps1` (Windows PowerShell 5.1 e Windows Forms) e `scripts/tray/SecondBrainTray.swift` (AppKit; `install_jobs.py` lo compila con `swiftc` in `~/Library/Application Support/second-brain/`, servono gli Xcode Command Line Tools). `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/tray/tray.ps1 -SelfTest` stampa il controllo della dashboard, il menu e il comando esatto di ogni voce senza mostrare nulla. La versione macOS non è ancora stata compilata né provata. Su Windows l'icona compare al prossimo login; per vederla subito: `schtasks /run /tn second-brain.tray`.

## Comandi

Avvia `claude` nella cartella del vault e scrivi:

| Comando | Cosa fa |
|---|---|
| `/nuovo-progetto <nome> [percorso]` | crea la cartella del progetto, il suo `STATE.md` e la riga in `projects/INDEX.md`; con un percorso scrive anche il campo `Repo:` (una riga per repo, per un progetto con più repo) |
| `/morning` | il brief del mattino: progetti, novità, priorità |
| `/chiudi-giornata` | riscrive gli STATE dai tuoi commit, lancia i controlli e committa in locale; non fa mai push |
| `/weekly-review` | cosa è avanzato, cosa è fermo, cosa è trascurato |
| `/cattura <testo>` | smista ciò che dici in piano, aree, decisioni e fatti da consolidare; scrive i legami tra task (`id:`, `dopo:`, `chi:te`) solo se li dici tu, in un commit a parte, e chiede per quelli dedotti; `/weekly-review` porta i fatti in `memory/` con un solo sì |
| `/post` | trasforma una nota in una bozza LinkedIn in `content/linkedin/` |
| `/bozze-settimana` | tre bozze di post per la settimana (LinkedIn e Instagram, come hai scelto) |
| `/commit-push-pr` | commit, push e apertura di una PR per un repo di codice, chiedendoti conferma prima del push |
| `/adotta-repo` | una tantum: elenca i repo git del computer che il vault non conosce e registra le tue risposte |
| `/kit [nome]` | installa i plugin e le skill di `kit/<nome>.md` (predefinito `lavoro`) a livello utente, una voce alla volta, dopo `scan-before-install` (serve `uv tool install skillspector`) e il tuo sì; con il kit lavoro prima chiede se la regola dell'azienda lo permette |

Subagenti: `researcher` (legge le novità e scrive schede in `radar/`), `reviewer` (rivede la settimana, non scrive), `writer` (bozze, solo con `/post`). Nessuno può lanciarne un altro.

**Registrare un piano approvato.** `python3 scripts/registra-piano.py <piano.md> --tag <progetto> --obiettivo <slug> [--titolo T] [--scadenza AAAA-MM-GG] [--giorni lun,mar,...|tutti] [--piano-rel <percorso>] [--senza-commit]` scrive nel vault un piano fatto con superpowers:writing-plans, da qualsiasi cartella. Il vault è sempre quello in cui sta lo script: `--vault` non c'è. Il file del piano deve stare in uno dei repo del progetto (le righe `Repo:` del suo STATE), mai in `projects/` del vault, nella cartella del lavoro o nella cartella riservata (ovunque sia, e dove porta se è un link), nemmeno attraverso un link, né nella cartella del lavoro, in `_private` o nella cartella riservata di `projects/` di un'altra copia di un vault. Il suo percorso relativo alla radice di quel repo diventa il `piano:` dell'obiettivo e si scrive sempre; `--piano-rel` è facoltativo e, se lo passi, deve essere lo stesso percorso. Ogni `### Task <N>: <titolo>` diventa `- [ ] #<progetto> <titolo del piano> · Task <N>: <titolo> id:<slug>-t<N> [dopo:...] obiettivo:<slug> [stima:...] [repo:...]` nella sezione «Prossimi giorni» di `docs/piano.md`, dopo l'ultimo task aperto del progetto in quella sezione, oppure in fondo alla sezione (che si crea se manca). Dentro un task lo script legge solo `**Dipende da:** Task 1, Task 3` (oppure `nessuna`), `**Stima:** 3h` o `1g` e `**Repo:** <nome>`; i blocchi di codice si saltano, e un titolo come `### Task 2 - B` che non è `### Task <N>: <titolo>` è un problema. La riga dell'obiettivo in `docs/obiettivi.md` prende il titolo, `scadenza:`, `giorni:` e `piano:`; un valore che non passi resta com'era, e un obiettivo nuovo prende il titolo del piano. Un obiettivo appartiene a un solo file di piano, il suo `piano:`: rilanciato sullo stesso file aggiorna le righe con lo stesso `id:` dove sono (testo e marcatori; la casella e una data scritta in testa restano) senza duplicarle. Un `piano:` che c'è già non cambia mai: un altro file di piano si ferma, e così un piano con gli id già in `docs/piano.md` quando l'obiettivo non ha ancora `piano:`. Per un altro piano usa un altro `--obiettivo`. Un task sparito dal piano è un avviso. Il piano è un dato non fidato: solo un file `.md` fino a 1 MB, al massimo 100 task, e il testo scritto segue le regole del «nuovo task» della mappa (al massimo 200 caratteri, niente `<` né `>`, niente caratteri di controllo o di direzione, nessuna parola che si leggerebbe come marcatore), e in più niente `[[`, `]]`, `|`, link Markdown, immagini né URL (`](`, `![`, `://`); un `#` nei titoli si toglie, così un piano non aggiunge un hashtag. Il progetto deve stare in `projects/INDEX.md`, non essere del lavoro né della cartella riservata; i nomi di `**Repo:**` devono essere repo di quel progetto. Con un problema qualsiasi non scrive niente, stampa una riga per problema con la riga del piano e cosa correggere ed esce con 2; un task senza `Dipende da` o `Stima` è un avviso. Esce con 1, dicendo il file, quando `config.json` non si legge (potrebbe nascondere la cartella riservata, quindi lo script rifiuta), quando `docs/piano.md` o `docs/obiettivi.md` non è UTF-8 valido o non si scrive, o quando il commit non riesce. Poi committa solo `docs/piano.md` e `docs/obiettivi.md` (`docs(piano): register plan <slug>`, con id e legami nel corpo), con git lanciato senza le variabili `GIT_*` di chi lo chiama; `--senza-commit` lo salta. I titoli registrati entrano nella storia git del vault: non mettere mai dati personali nei titoli di un piano. Lo script e la dashboard non si bloccano a vicenda: non spuntare né aggiungere task dalla dashboard mentre si registra un piano. Niente rete.

Le tue competenze seguono i progetti. La colonna *Stack* di `projects/INDEX.md` viene confrontata con la riga *Skills* di `memory/about-me.md`: `/nuovo-progetto` chiede lo stack e propone le tecnologie che non hai ancora; `/chiudi-giornata` fa lo stesso se ci sei, e nella run non presidiata scrive solo una riga per tecnologia mancante in *Da confermare* del `daily/` di oggi (per esempio: ``Aggiungere `Postgres` alle competenze in memory/about-me.md (da progetto api-ordini)``). `memory/about-me.md` cambia solo dopo il tuo sì, voce per voce. La cartella riservata non è nell'indice, quindi per questo non viene mai letta. Una tecnologia che rifiuti torna nel primo giorno con attività: non c'è ancora un elenco delle voci rifiutate.

## Job pianificati

`scripts/jobs.json` definisce i job una volta sola; `python3 install_jobs.py` li registra nello scheduler del tuo sistema: launchd su macOS, timer utente di systemd su Linux, Utilità di pianificazione su Windows. Comincia con `python3 install_jobs.py --dry-run` per leggere cosa farebbe. `python3 install_jobs.py --uninstall` li toglie. Ogni job si può lanciare due volte senza danni, quindi recuperare dopo che il computer era spento non fa male. I job di un modulo che hai scelto si registrano; gli altri facoltativi vogliono `--all`.

| Job | Quando | Cosa fa |
|---|---|---|
| `second-brain.morning` | feriali 08:00 e al login (macOS e Windows; su Linux non ancora) | l'avvio del mattino: chiude il lavoro in sospeso, crea la nota del giorno |
| `second-brain.chiusura` | feriali 18:30 | `/chiudi-giornata`: riscrive gli STATE dai tuoi commit |
| `second-brain.pulizia` | venerdì 18:00 | controllo settimanale e rapporto |
| `second-brain.dashboard` | al login, sempre acceso | la dashboard locale |
| `second-brain.feed` (facoltativo, scelto al setup) | lunedì 07:00 | `scripts/feed.py`: raccoglie le novità di `memory/feeds.md` in `inbox/` (raccoglitore incluso; saltalo se usi n8n) |
| `second-brain.radar` (facoltativo, scelto al setup) | lunedì 07:30 | filtra le novità in `inbox/` per i tuoi progetti, con i modelli che hai scelto |
| `second-brain.bozze` (facoltativo, scelto al setup) | lunedì 08:30 | `/bozze-settimana`: tre bozze di post |
| `second-brain.tray` | al login (macOS e Windows) | l'icona nella barra (vedi «La dashboard»); «Esci» la chiude fino al prossimo login |

Il testo di una novità non è fidato: ogni titolo passa da `content-guard` (schemi di istruzioni nascoste) prima che un modello lo veda. I log stanno in `~/Library/Logs` (macOS), `$XDG_STATE_HOME/second-brain` o `~/.local/state/second-brain` (Linux), `%LOCALAPPDATA%\second-brain\logs` (Windows).

## Controlli

- `python3 scripts/check` è il controllo unico da lanciare prima di un commit o di una pull request: `scripts/verify`, il linter ([ruff](https://docs.astral.sh/ruff/), regole in `ruff.toml`), i test degli script, i test del template e una scansione gitleaks della storia git, come il job della CI (i file ignorati da git non si scansionano; un ritrovamento mostra file e riga, mai il segreto). Si ferma al primo passo rosso e dice quale. Servono ruff e gitleaks: `doctor.py` li elenca come facoltativi e stampa il comando per installarli, con la versione di ruff usata dalla CI.
- `python3 scripts/verify` controlla le regole del vault: STATE corti, `INDEX` coerente, riga `Harness` valida dove c'è, link validi, che questo README citi ogni job e ogni comando, e il registro `scaffold/` se ce l'hai. Le dipendenze rotte in `docs/piano.md` (un `id:` doppio, un `dopo:` che non punta a nulla, un ciclo), un `obiettivo:` che `docs/obiettivi.md` non definisce, un `repo:<nome>[,<nome>…]` su un task senza `#tag` di progetto o che nomina qualcosa che non è un repo di quel progetto (il nome breve è il nome della cartella di una riga `Repo` del suo `STATE.md`) e le righe non valide di quel file sono avvisi, stampati come `docs/piano.md:<riga>: avviso: ...` (`docs/obiettivi.md:<riga>: avviso: ...` per le righe di quel file): non lo bloccano e non cambiano l'exit. `docs/obiettivi.md` elenca gli obiettivi a cui puntano i marcatori `obiettivo:<slug>` del piano, uno per riga come `- slug: titolo` (titolo fino a 120 caratteri; le altre righe si ignorano). Una riga di obiettivo può finire con dei marcatori, letti dal fondo come quelli dei task (la lettura si ferma al primo non valido o ripetuto): `scadenza:AAAA-MM-GG` (la scadenza), `giorni:` con un elenco separato da virgole di `lun,mar,mer,gio,ven,sab,dom` oppure `giorni:tutti` (i giorni di lavoro dell'obiettivo; senza, vale il calendario del vault) e `piano:<percorso>` (il file del piano, relativo alla radice del repo: lettere, cifre, `.`, `_`, `-` e `/`, al massimo 200 caratteri, senza spazi, senza `..` e non assoluto), come in `- rilascio: Rilascio 1.0 scadenza:2026-12-04 giorni:lun,mar,mer piano:docs/piano.md`. La stima di un task è il suo marcatore `stima:<n>h` o `stima:<n>g` (`9h`, `1,5g`), e un giorno vale `ore_giorno` ore. Il calendario del vault sta in `config.json` come `"piano": {"ore_giorno": 6, "giorni_lavoro": ["lun", "mar", "mer", "gio", "ven"]}`, che sono anche i valori di fabbrica; `ore_giorno` va da 1 a 24. Per un obiettivo con scadenza le date dei suoi task aperti si calcolano, mai scritte nel piano: un task va finito entro la scadenza meno i giorni lavorativi che servono ancora ai suoi successori aperti dello stesso obiettivo (la catena più lunga delle loro stime), un task senza stima conta zero ore, e si assume che i task indipendenti procedano in parallelo. Anche un marcatore di obiettivo o un'impostazione `piano` non validi sono avvisi (`docs/obiettivi.md:<riga>: avviso: ...`, `config.json: avviso: ...`): l'obiettivo resta definito, un `giorni:` non valido usa il calendario del vault e un'impostazione non valida il suo valore di fabbrica. Un repo il cui nome di cartella non si può scrivere come marcatore `repo:` (oltre 60 caratteri, o caratteri diversi da lettere, cifre, `.`, `_` e `-`) è un avviso sul suo STATE (`projects/<progetto>/STATE.md: avviso: repo:<nome> non si può scrivere come marcatore: rinomina la cartella`): la dashboard lo elenca, ma nessun task può nominarlo con `repo:`. Due righe `Repo` dello stesso progetto con lo stesso nome di cartella sono invece un errore che lo blocca, perché è il nome con cui si controlla un `repo:`. `projects/_archivio/` contiene i progetti archiviati dalla dashboard: non si confronta con `INDEX`, e un link scritto quando un progetto stava ancora in `projects/<nome>/` (in una nota del giorno, per esempio) resta valido dopo l'archiviazione. Lancialo dopo ogni modifica a uno STATE o all'indice; `/chiudi-giornata` lo lancia per te.
- `python3 doctor.py` controlla Python, git, Claude Code, `verify` e ciò che le tue scelte richiedono (Ollama acceso, ogni modello locale scaricato, RAM sufficiente, n8n se l'hai scelto). `--ci` controlla solo il necessario.
- Controllo dei segreti: `scripts/hooks/pre-commit` lancia gitleaks su ciò che stai per committare e blocca il commit se trova un segreto. Si attiva una volta per clone con `git config core.hooksPath scripts/hooks`; serve [gitleaks](https://github.com/gitleaks/gitleaks) installato (`doctor.py` mostra come). `doctor.py` dice anche quando l'hook non è attivo in questo clone: un clone o un worktree nuovo committa senza questi controlli finché non lanci quel comando. Ti dice anche quando la barra di stato in `~/.claude/settings.json` lancia un Python o uno `statusline-uso.py` che non c'è più (una cartella rinominata o cancellata): Claude Code non mostra errori, la pagina dell'uso resta ferma ai numeri vecchi. Stampa lo `statusLine` da incollare.

## Traccia i repo che hai già

Il modulo `scaffold` è facoltativo. Crea `scaffold/registro.md` (i template di progetto da cui parti, vuoto), `scaffold/profili/personal.md` e `scaffold/profili/lavoro.md` (cosa fare per i progetti tuoi e per quelli di lavoro; il lavoro non ha funzionalità AI né repo remoto), `scaffold/ignorati.md` (i repo a cui hai detto «ignora» o «non ora») e `scaffold/hook-avvio.md`.

- `/adotta-repo` chiede dove cercare, elenca i repo git che il vault non conosce (quelli con lo stesso remote sono raggruppati) e registra la tua risposta per ciascuno: tracciarlo, ignorarlo, richiederlo tra 7 giorni, oppure «lavoro». Per un repo di lavoro si salva solo l'impronta del percorso, mai il percorso né il nome.
- `scripts/blocchi-regole.py` conta quante volte ogni regola dell'hook ha negato un comando o chiesto conferma (`--giorni N`, predefinito 7; `--json`). L'hook scrive una riga per blocco in `second-brain-regole.log` nella cartella dei log: la data, il nome della regola e l'azione, mai il comando né un percorso. La chiusura serale passa i conteggi di oggi a `/chiudi-giornata`; `/weekly-review` usa quelli della settimana per chiedere quali blocchi erano falsi positivi. `git config core.hooksPath` senza un valore legge soltanto l'impostazione e non viene più negato.
- `scripts/harness-progetti.py` dice a che punto è ogni progetto con l'harness per agenti (i controlli e i guardrail che permettono a un agente di lavorare in sicurezza in un repo). La decisione è una riga facoltativa nello `STATE.md` del progetto: `- **Harness:** da decidere`, `adeguare (data)` oppure `non adeguare questo progetto (data)`. Il rifiuto vale solo se scritto per esteso; una riga assente vuol dire «non ancora deciso». Lo stato viene da `.claude/harness-status.json` nel repo del progetto, il riepilogo che lascia un audit: lo script ne legge quattro numeri e una data, nient'altro, e un file che non torna vale «da valutare». Non scrive mai, non esegue nulla del repo, salta le cartelle del lavoro e riservata in qualunque maiuscola e non tocca mai un repo su un percorso di rete; quando `config.json` non si legge o ha una forma inattesa non legge nessun repo, lo dice su stderr ed esce con 1. `scripts/attivita-progetti.py` (l'attività dei progetti letta dalle routine del mattino e della sera) segue le stesse regole: nessuno STATE riservato si legge, un repo di rete si salta prima di lanciare git, e con `config.json` illeggibile non stampa niente ed esce con 1. Con `--json` stampa un elenco.
- `scripts/repo-non-tracciato.py` dice se la cartella corrente è un repo git non tracciato. Non scrive mai da solo. Con l'hook di `scaffold/hook-avvio.md` Claude Code può ricordartelo quando apri un repo così. Quell'hook tocca le impostazioni globali `~/.claude`, quindi il wizard **non** lo installa: il file mostra le due righe da incollare e decidi tu.
- Un repo è «tracciato» quando il suo percorso sta in una riga `Repo:` di un `projects/*/STATE.md`.
- Un progetto può comprendere più repo (per esempio backend, app e frontend): scrivi una riga `- **Repo:** <percorso>` per ogni repo, una sotto l'altra, un percorso assoluto per riga. `/chiudi-giornata`, l'avvio del mattino, `/weekly-review` e la dashboard leggono i commit di tutti, e nessuno risulta non tracciato. In `/adotta-repo` un «sì» può aggiungere il repo a un progetto che esiste già invece di crearne uno nuovo.

  ```markdown
  - **Repo:** /srv/codice/negozio/backend
  - **Repo:** /srv/codice/negozio/app
  - **Repo:** /srv/codice/negozio/frontend
  ```

## Agenti da remoto dal telefono (facoltativo)

Con [Paseo](https://paseo.sh), un daemon open source con app iOS e Android, puoi avviare e seguire dal telefono agenti Claude Code sui tuoi progetti. Il second brain prepara il contesto e il prompt; tu avvii l'agente dall'app; la chiusura serale vede i suoi commit come sempre. Nel vault non cambia nulla. Leggi [docs/remote-agents-paseo.md](docs/remote-agents-paseo.md) (in inglese) **prima di installarlo**: le impostazioni predefinite di Paseo (nessuna password, strumenti di controllo degli agenti, aggiornamenti Windows non firmati) vanno irrobustite, e la guida elenca le impostazioni esatte per Windows, macOS e una VM Linux.

## Sistemi supportati

| Parte | macOS | Linux | Windows |
|---|---|---|---|
| Vault, `scripts/verify`, `setup.py`, `doctor.py` | sì | i test CI passano | i test CI passano |
| Dashboard | sì | in parte (niente stato dei job) | in parte |
| Calendario: `macos` | sì | no | no |
| Calendario: `ics` e `caldav` | provati con dati finti e un server finto | uguale | uguale |
| Job pianificati (`install_jobs.py`) | sì | file generati e testati, non ancora registrati davvero | uguale |
| Job del mattino (`second-brain.morning`) | sì | non ancora | file generato e testato, non ancora registrato davvero |
| Icona nella barra (`second-brain.tray`) | scritta, non provata (mai compilata) | no | provata: self-test e un avvio vero, voci del menu non ancora cliccate |

«I test CI passano» vuol dire test automatici su un computer pulito, non che qualcuno l'abbia usato. Se lo provi su Linux o Windows, segnala cosa si è rotto.

## Privacy

Claude Code invia al modello i file che legge. Metti le note riservate nella cartella creata dal modulo `riservata` (esclusa da git e bloccata da regole `deny`) e leggi [ADR-002](docs/adr/ADR-002-confidential-notes.md) per i limiti di quel blocco: le regole non fermano uno script che lanci tu. `scripts/elabora-richieste.py`, che trasforma le richieste di post della dashboard in bozze con `claude -p`, salta le cartelle del lavoro e riservate; quando `config.json` esiste ma non si legge non elabora niente e il suo giro risulta fallito, perché la cartella riservata non si conosce. Il tuo nome, le note e i file di memoria restano nella tua copia: `setup.py` li scrive dai file `*.example.md` e git li ignora. Gli indirizzi dei calendari e le password stanno fuori dal vault. La dashboard ascolta solo su `127.0.0.1`. Le sue pagine non mostrano mai il testo grezzo di un errore: arrivano solo codici noti e frasi fisse. Un calendario che non si legge dà in Agenda un motivo fisso (per esempio «manca il file dei calendari (vedi la guida)» o «il file dei calendari è leggibile da altri utenti: chmod 600 (vedi la guida)») invece di nominare il file o i calendari, e il log della dashboard riceve solo la classe dell'errore e l'identificativo di quel motivo; un modello che non risponde dice di controllare `modelli.assistente` in `config.json`. La regola della cartella riservata viene da `moduli.py` nella radice del vault: se quel file manca, gli avvii e gli script che leggono i progetti si rifiutano, e gli script dicono che manca `moduli.py`. **Rischi che restano** nei controlli sulla cartella riservata: un link o una junction locale che porta a una condivisione di rete si segue quando il percorso si risolve, prima del controllo sul percorso risolto; su macOS e Linux una condivisione di rete montata sembra una cartella locale (si riconoscono solo i percorsi `//server` e, su Windows, `\\server` e le lettere di unità collegate); un hard link a un file riservato non si distingue dal file stesso. Il plugin Sync di Obsidian è spento in `.obsidian/`: accenderlo sincronizzerebbe anche la cartella riservata, che git ignora.

## Se qualcosa non va

- **`python3` non trovato su Windows**: usa `py -3`.
- **Errore di certificato nel leggere i feed su macOS**: il Python di python.org non ha i certificati; il raccoglitore ripiega su quelli di sistema. Se ancora fallisce, lancia `Install Certificates.command` dalla cartella di Python in Applicazioni.
- **`doctor.py` dice che Ollama manca o non è acceso**: avvia l'app Ollama, oppure scegli `none` per quel passo con `python3 setup.py --add radar`.
- **Manca un modello**: `ollama pull <modello>` (il nome è nel messaggio di `doctor.py`).
- **L'assistente dice che non conosce i tuoi appuntamenti**: non c'è un calendario collegato, il calendario non si legge, oppure il modello è `claude` e non hai permesso di inviare gli appuntamenti. `config.json` mostra `calendario.provider` e `moduli.assistente`.
- **«è leggibile da altri utenti»**: `chmod 600` su quel file.
- **Su Windows `./scripts/verify` non parte dentro Claude Code** (Git Bash non riesce a lanciare il `python3` dello shebang): usa `py -3 scripts/verify`. I comandi e i permessi lo prevedono già.
- **Su Windows i job girano senza finestra**: l'Utilità di pianificazione li avvia con `conhost.exe --headless`, quindi non compare nessuna finestra CMD vuota. Se un job registrato prima di questa modifica ne apre ancora una, lancia di nuovo `py -3 install_jobs.py` per registrarlo di nuovo.
- **Perché il job della tray usa `-ExecutionPolicy Bypass`**: il criterio predefinito di Windows (Restricted) blocca ogni script, anche `tray.ps1`. Il bypass vale solo per quel processo PowerShell e solo per quel file di questo repo; non cambia il criterio del sistema. Firmare lo script lo eviterebbe, ma per ora è fuori dal perimetro. Se la tua organizzazione lo vieta, togli solo questo job: `py -3 install_jobs.py --uninstall --only tray`.
- **`scripts/verify` protesta**: il messaggio nomina il file e la riga; correggi e rilancialo.
- **I job non girano su Linux quando sei uscito**: `loginctl enable-linger $USER`.

## Aggiornare e disinstallare

Aggiornare: `git pull`, poi `python3 doctor.py` e `python3 scripts/verify`. I tuoi file sono ignorati da git o non toccati dal pull. Disinstallare: `python3 install_jobs.py --uninstall`, poi cancella la cartella. Su macOS cancella anche `~/Library/Application Support/second-brain/` (l'icona compilata). Claude Code e Ollama hanno le loro guide di disinstallazione.
