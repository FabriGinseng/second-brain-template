# second-brain-template

A starter kit for a personal "second brain": an Obsidian vault of plain Markdown, kept up to date by an AI coding agent ([Claude Code](https://claude.com/claude-code)) under rules you control. Italian version: [README.it.md](README.it.md).

> **Status: v0.1.** The vault structure, the setup wizard, the checks and the local dashboard work. Scheduled jobs are generated for macOS, Linux and Windows. Used daily on macOS. On Linux and Windows the automated tests pass in CI, but nobody has used the installer there for real yet: see "Platform support". Nothing here has been tested against a real iCloud, Nextcloud or Fastmail account.

> **Languages.** The documentation is bilingual: this file in English, [README.it.md](README.it.md) in Italian. The files the system writes and reads (`STATE.md`, daily notes, command texts, `scripts/verify` messages) are in Italian in v0.1; the ADR defaults are in English. Translating them is not planned yet.

## What you get

- **Projects**: one short `STATE.md` per project, rewritten (never appended), a dated `decisions.md`, and a row in `projects/INDEX.md`.
- **Rules the agent follows**: a short `CLAUDE.md`, decisions in `docs/adr/` (confidential notes, autonomy level), a glossary.
- **Rules enforced by a hook**: `.claude/hooks/regole.py` with its list `regole.json` (ADR-012) asks before push, PRs, deploys and `rm` and refuses force-push and history rewrites, in every repo once `scripts/installa-regole.py` has run (setup offers it). `.claude/settings.json` guards the confidential folder.
- **A learning loop** (ADR-015): a mistake somebody had to correct leaves one dated line in "Recurring errors" of `CLAUDE.md`; the second time the same cause shows up it becomes a rule, and a rule that can be verified becomes a check. `/chiudi-giornata` proposes the line, `/weekly-review` proposes the rule or the check, and nothing is written without a yes.
- **A check**: `scripts/verify` verifies the vault rules. No model, files only.
- **Commands and subagents** in `.claude/`: see "Commands". The command texts are in Italian in v0.1.
- **A local dashboard** (Python standard library, `127.0.0.1` only): projects, plan, today, radar, services and limits, posts, and an assistant panel. It shows only the pages of the modules you chose.
- **`setup.py` and `doctor.py`**: a first-run wizard made of modules, and a check of what your choices need.

## Requirements

- Python 3.9 or newer and git.
- [Claude Code](https://code.claude.com/docs/en/setup) with a paid Claude plan (the free plan does not include it). The agent, the weekly drafts and the `claude` model choice use it and your plan quota.
- Optional, only if you pick the matching feature: [Ollama](https://ollama.com) for local models; Chrome, Chromium or Edge for the post images; [Obsidian](https://obsidian.md) to read the notes in a nice interface; n8n only if you prefer it to the built-in news collector.

`python3 doctor.py` tells you what is missing and prints the official install command for your system. It never installs anything by itself.

## Install step by step

The same four steps on every system; the details differ only for the first one.

1. **Install Python, git and Claude Code.** Check with `python3 --version`, `git --version`, `claude --version` (on Windows `py -3 --version`).
2. **Get the template.** `git clone https://github.com/FabriGinseng/second-brain-template.git my-second-brain`, then `cd my-second-brain`. You can open that folder as a vault in Obsidian.
3. **Run the wizard.** `python3 setup.py` (Windows: `py -3 setup.py`). It asks for the language, your name and role, then offers each optional module with a yes or no. Before it writes anything it shows a summary and waits for your yes. It never overwrites a file that exists.
4. **Check.** `python3 doctor.py`, then `python3 scripts/verify`, which must print `OK`.

Then follow [GETTING_STARTED.md](GETTING_STARTED.md): about 15 minutes, each step says what you should see.

### macOS

Python: `brew install python`, or the installer from python.org (see the note in "Troubleshooting"). git: `xcode-select --install`. Claude Code: `curl -fsSL https://claude.ai/install.sh | bash`. Everything in this guide works here, including the calendar from the Calendar app.

### Linux

Python and git from your package manager (for example `sudo apt install python3 git`). Claude Code: the same `curl` command as above. Scheduled jobs use systemd user timers: run `loginctl enable-linger $USER` once so they also run when you are not logged in. For the post images install Chromium or Chrome.

### Windows

Use `py -3` where this guide says `python3`. Python: `winget install Python.Python.3.12`. git: `winget install Git.Git`. Claude Code: `irm https://claude.ai/install.ps1 | iex` in PowerShell. Native Windows is the least tested path: WSL 2 is the safer choice for Claude Code until it has been tested for real.

## The setup wizard and its modules

`python3 setup.py --list` shows the modules and what each one does; `python3 setup.py --add <module>` adds one later without touching what you already have. A module can only ask you questions and then do a few fixed things (write a setting, create a folder or a file that does not exist, add a line to `.gitignore`, add `deny` rules). It cannot run commands.

| Module | What it asks | What it does |
|---|---|---|
| `core` (always) | your name, role, language | `config.json`, `memory/` files, your name in `CLAUDE.md` |
| `riservata` | the name of a confidential folder | creates it, git-ignores it, blocks Claude Code from reading and editing it |
| `radar` | topics, feed addresses, who collects the news, which model for each step | the Monday radar: news from your feeds, filtered for your projects, one short card each in `radar/` |
| `bozze` | LinkedIn, Instagram or both | the Monday drafts in `content/`; never publishes |
| `servizi` | nothing | the Services page of the dashboard |
| `assistente` | which model answers, which calendar, and whether appointments may go to Claude | the assistant panel in "Today" |
| `scaffold` | nothing | a registry of project templates, two profiles (`personal`, `lavoro`) and a reminder for repos the vault does not know: see "Track the repos you already have" |

**After the questions, the wizard prepares the computer.** It scans RAM, free disk, CPU and graphics card (nothing else, nothing is sent anywhere) and uses that to suggest a local model: about 8 GB of RAM gets a 4B model, 16 GB or more `qwen3:8b`, less than that Claude or no model, and no download is offered if the disk is nearly full. Then, one step at a time, it asks before doing each of these and shows the command it would run: install Ollama or Obsidian if you chose something that needs them (with `brew` on macOS, `winget` on Windows, `flatpak` on Linux), download the local models you picked (`ollama pull`), turn on the secret scan before commits, add the Claude usage status line to `~/.claude/settings.json` (a copy of the file is kept), register the scheduled jobs, and run the radar once so its page has something to show. You can say no to any step and do it later by hand. It does **not** run installers that are downloaded from the internet and piped into a shell: for Claude Code (and Ollama on Linux) it prints the official command and you run it yourself. With `--yes` or `--answers` it never installs anything.

You can also run the wizard without questions: `python3 setup.py --answers answers.json --yes`. `tests/risposte-tutti.json` is a complete example. `python3 setup.py --dry-run` shows what would happen and changes nothing. `python3 setup.py --clean-example` removes the example project when you have your own.

## Local or Claude: who answers what

Every step that needs a model has its own setting in `config.json` (`modelli`), and the default is `none`: no model, nothing leaves your computer, nothing to download.

| Choice | What happens | Cost |
|---|---|---|
| `none` | the radar matches keywords and you read every candidate; the assistant panel stays off | nothing |
| `ollama:<model>` | everything stays on your computer; slower and less precise | disk space and RAM |
| `claude` | more precise; the text of that step leaves your computer for Anthropic | your plan quota |

What is sent with `claude`: for the radar, the titles of the news and the stack and goal of your projects; for the assistant, your question and, only if you allowed it at setup, the titles and times of your appointments. The confidential folder is never sent by any step. Dates, weekdays and free hours are computed by the code, not by the model, because a model gets them wrong.

With `radar_giudizio` set to `claude` (or `claude:haiku`) the radar is one step instead of two: every Monday `scripts/radar.py` runs `scripts/feed.py` (each news item comes with a short summary, and title and summary go through `content-guard`) and then `scripts/radar-claude.py`, one call on the whole inbox. The model answers only with the item number and a few short fields, and the code checks them: the title and link of a card always come from the inbox. A card (at most 8 a week) names the projects, the type (`progetto`, `skill`, `sicurezza`), what it is, what to do with it and what it costs to try. The dashboard shows the card and lets you vote Useful or Not useful (`radar/feedback.jsonl`), and `/morning` lists the cards in the brief. With a local model the two stages stay. With n8n collecting the news, `feed.py` does not run on its own. Good feeds for a developer: the release feeds of your own packages (`https://github.com/<owner>/<repo>/releases.atom`), `https://nodejs.org/en/feed/vulnerability.xml` and `https://github.com/anthropics/claude-code/releases.atom`.

`python3 scripts/modello.py --ram` suggests a local model for your RAM (about 8 GB: a 4B model; 16 GB or more: `qwen3:8b`). These are thresholds, not measurements on your machine. `python3 scripts/modello.py --check-model <step>` runs three fixed test requests and tells you whether the model you chose is suitable. To download a model: `ollama pull <model>`.

## The assistant and your calendar

The panel in "Today" answers questions about your day ("what is due this week?", "when am I free tomorrow?") and can propose an appointment that you confirm with a click. It has no tools and no web: it only sees a text the code prepares. The model can be wrong, and the page says so.

The calendar goes through `scripts/calendario.py`. Choose a provider in `config.json` (`calendario.provider`) or in the wizard:

| Provider | Systems | Reads | Writes | Needs |
|---|---|---|---|---|
| `macos` | macOS | yes | yes | the Calendar app (Google and iCloud accounts already in it) |
| `ics` | all | yes (repeating events too) | no | the secret iCal address of a calendar, or a `.ics` file |
| `caldav` | all | yes | yes | server, user and an app password (iCloud, Nextcloud, Fastmail) |
| `none` | all | no | no | nothing: the assistant says it does not know your appointments |

The addresses and passwords are credentials. They live **outside** the vault, which goes into git: `~/.config/second-brain/` on macOS and Linux, `%APPDATA%\second-brain\` on Windows, in files readable only by you (`chmod 600`; otherwise the provider refuses to read them).

- `calendari.json` for `ics`: `{"calendari": [{"nome": "Personal", "url": "https://..."}, {"nome": "Holidays", "file": "/path/holidays.ics"}]}`. In Google Calendar the address is under the calendar's settings, "Secret address in iCal format". Only `https://` addresses are accepted.
- `caldav.json` for `caldav`: `{"server": "https://caldav.icloud.com", "utente": "you@example.com", "password": "app password"}`. Only `https://`, redirects are not followed, a server that points to another domain is refused, and no error message shows the password.

If a calendar cannot be read, the assistant does not answer about free hours instead of telling you that you are free when you are not. If the model is `claude` and you did not allow it at setup (`moduli.assistente.calendario_al_cloud`), the assistant does not receive your appointments. Google Calendar outside the Mac is not supported for writing; reading works through the secret iCal address. Repeating rules the reader does not understand (for example "second Tuesday and fourth Thursday") are shown as a warning in "Today", not ignored in silence.

## The dashboard

`python3 scripts/dashboard/server.py`, then open http://127.0.0.1:8765. It listens only on your computer. The menu shows the pages of the modules you chose; a page you did not choose is not there. `second-brain.dashboard` (see "Scheduled jobs") keeps it running: if it stops, even cleanly, it comes back by itself (launchd KeepAlive, systemd `Restart=always`, on Windows a check every 10 minutes). On Linux and Windows the job status buttons stay empty because they use launchd.

**The map.** Every project and topic is a node; its tasks from `docs/piano.md` sit around it when you hover or select it. A task has one of four states, read from its dependencies (`id:`, `dopo:`, `chi:te`): **ready** (solid grey: nothing left to wait for), **in progress** (amber), **waiting** (thin dashed grey: a task it depends on is not `[x]` yet) and **done** (green). The ring around a node has one segment per state, waiting is dashed so it does not rely on colour, and the number in the middle counts the ready tasks; the node's tooltip and the panel say "N pronti · M in corso · K in attesa". The panel groups a node's tasks as "Pronti da avviare", "In corso", "In attesa" and "Fatti" (folded). A waiting row says what it waits for ("aspetta: <task>", with the node when it is another one, or "aspetta: te — <task>" when it is a task of yours); a broken `dopo:` or a cycle shows "riferimento rotto: <id>" or "ciclo di dipendenze". Selecting a waiting task draws the dependency thread: an arrow from each other node it waits on, and a highlighted dot for a blocker in the same node, one task at a time. Below 760 px the map becomes a list with the same states, groups and reasons. "Avvia in Claude" only appears on ready or in-progress tasks: the server refuses (HTTP 409) a task that waits, has a dependency error, or is your own (`chi:te`, labelled "Tocca a te"). Ticking a task by hand is always allowed. It opens Claude in the task's repo: the one its `repo:` marker names, or the project's only repo. When there is more than one to pick from, the server answers 409 and asks you to choose ("Scegli il repo in cui avviare."); the name sent back is accepted only if it is one of those repos, never read as a path. A listed repo whose folder is missing is refused, not swapped for the vault, which stays the folder of a project with no repo. In a project where two `Repo` lines share a folder name, only a task whose `repo:` names one of the other repos launches; any other task is refused, whatever repo you pick, and its "Avvia" dialog says so instead of offering a choice: "Due repo di questo progetto hanno lo stesso nome (<names>): rinomina una delle cartelle o togli una riga Repo dallo STATE.", with "Avvia" off. The map receives only the twin names (`repoDoppi`), never their paths. Claude never starts in a disk root, inside the work folder or `_private` of `projects/` or the confidential folder chosen at setup, wherever in the vault it is (a link that leads there included, and, when one of these folders is itself a link or junction, the folder it leads to), or in a folder that contains one of them other than the vault root: those notes never go to a cloud model ([ADR-002](docs/adr/ADR-002-confidential-notes.md)). A repo on a network share (`\\server\share` or a drive letter mapped to one, on Windows) is refused before it is touched, and when `config.json` exists but cannot be read, has an unexpected shape, turns the `riservata` module on without a folder or names a folder the setup would refuse, the confidential folder is unknown, so no task launches until it is fixed ("config.json non leggibile o non valido: l'avvio è sospeso finché non lo correggi."; the map still loads). The confidential folder is recognised whatever its case and separator: `Projects/Secret` or `projects\Secret` is the folder `projects/secret`, and a row of `INDEX.md` with that name is treated like a work project (its STATE is not read, its tasks do not launch). Such a repo is refused ("Cartella non valida per questo task.") and Claude opens in the folder the check approved, with links resolved. A node with more than one repo shows their names under its type (three at most, then "+k"; the full list is in the tooltip of the node and of that line). Each task row has a label for each of its valid repos and "repo sconosciuto: <name>" for a `repo:` the project does not have; a ready task that shares a repo with an in-progress task of the same node carries "stesso repo di un task in corso", a warning, not a block. A repo name longer than 24 characters is cut with "…" on the label and on the filter button; the full name is in the tooltip and is what screen readers read. In the panel of a node with more than one repo, above the tasks, the "tutti / <repo>…" filter shows the tasks that touch that repo plus those with no valid repo, and those without any `repo:` are marked "repo non indicato". The "Avvia" dialog says "Repo: <name>" when there is a single repo; when there are more it shows a choice of names only, none selected, and "Avvia" stays disabled until you pick one. The candidates are the task's valid `repo:` names when it has more than one, otherwise every repo of the project; if the plan changed and the server still asks for a choice, the dialog opens again with the repos to choose from. Clicking a node, or Enter or Space on it, selects it and the map glides (about 0.3 s; a jump when the system asks for reduced motion) to frame the node and its tasks; clicking the background, Escape or "Torna alla prossima azione" glides back to the view from before, and the wheel, a drag, a pinch or "Adatta" stops the glide where it is. Below 760 px nothing zooms: the list is shown. The rest of the motion only follows something you did, lasts at most 0.3 s and is off when the system asks for reduced motion: the tasks of a node fan out of it when the pointer opens it (never when you move with Tab), the node you select keeps a grey ring, the panel fades to its new content, the dependency thread draws in, and the goals a pill shows or hides fade in and out. Loading or refreshing the map never animates. Every node that can take a task (a node with a folder whose name is a valid tag) has a "+" at the top right of the disc that adds one, whatever it already holds. In a panel a long task title wraps on its own and its date and marks go under it.

**Goals on the map.** A task marked `obiettivo:<slug>` in `docs/piano.md` belongs to a goal; the goals are listed in `docs/obiettivi.md`. Goals sit in a band above the nodes as rounded boxes, with light dashed lines to the nodes they touch. Each box shows the title and a bar with one segment per state, in the order done, in progress, ready and waiting (dashed, like the ring), and under it "N di M fatti", and the full split is in the tooltip and in the label for screen readers, "<title>, obiettivo: N pronti · M in corso · K in attesa · F fatti". A goal used in the plan but missing from `docs/obiettivi.md` still shows, titled with its slug, with a dashed outline and "non definito"; a defined goal with no task shows an empty bar and "nessun passo". The "Obiettivi" filter shows the goals and only the nodes they touch ("Tutto" and "Aperti" show the goals too, "Progetti" and "Argomenti" do not). A task row with `obiettivo:`, in a node's panel and in the list, has a small "obiettivo: <title>" button (the title cut at 24 characters, whole in the tooltip): clicking it, or Enter or Space, selects that goal, shows it in the band even if a pill had folded it, and opens its panel; under "Progetti" or "Argomenti", which draw no goals, it first switches the map to "Tutto". Selecting a goal (clicking its box opens it as a graph, see below) turns its lines solid, fades the other nodes and opens its panel: the title, "obiettivo · <projects>", the counts, "Aggiungilo in docs/obiettivi.md" when it is not defined, and its tasks from every project in the same groups as a node, each labelled with its node, or "Nessun passo nel piano con questo obiettivo." when it has none. "Avvia" there launches Claude in the task's repo, picked by the same rule and the same dialog as in its node's panel. Below 760 px the list shows the goals before the nodes, each with its open tasks grouped by step as in the graph below ("Passo 1 — in parallelo: 3 task"), the done ones folded at the end. A goal is never a node: it can share its name with a project without being confused with it, and goals do not change the counts at the top or the tasks of each node.

**Deadlines on the map.** A goal with `scadenza:` in `docs/obiettivi.md` shows "scade <day>" on a line of its own under the bar. A goal "a rischio" needs more working days than are left before its deadline, or has open tasks past it: the box gets a bold "a rischio" next to the date and a warning outline; past the deadline it says "scaduto" instead, with a red outline. When the date and the word do not fit the width of the box (a narrow map, a larger font), the word goes on a line of its own and that box grows by one line. The state is always a word, never a colour alone, and it is also in the tooltip and the screen-reader label. The goal's panel starts with the deadline and the same word, "servono N giorni, ne restano M" (working days, today and the deadline included), the sentence "Le date ipotizzano che i task indipendenti procedano in parallelo." and the goal's plan file (`piano:`) as plain text. A task row, in the panel and in the list, shows "entro il <day>" when its date is computed, in red and preceded by "in ritardo" once a ready task is past it, and "senza stima" when it has no `stima:` and so counts zero hours; a hand-written date at the head of the line wins and shows as before. A goal without a deadline shows no date and no risk. The band stays short: goals whose tasks are all done fold into one "+k completati" pill, and past two rows of open goals the rest fold into "+k altri". Each pill is a button (Enter or Space) that shows its goals and, pressed again, folds them back; the nodes are laid out below the rows actually drawn. A selected goal is never folded away. Below 760 px the list shows every goal, with its deadline and state.

**A goal as a graph.** Clicking a goal box in the band (or Enter or Space on it) opens the goal as a graph over the map, top-down. On top sits the goal itself, with its counts, its deadline and "a rischio" when it is at risk. Below it, the goal's tasks in rows by dependency: the first row is what waits on nothing shown, each next row what waits on the row above at most, so the tasks of one row can run in parallel. A row too wide for the map wraps onto more lines, tied by an "in parallelo" bracket on the left. Arrows run from the blocking task to the one that waits; light lines join the goal to the first line of its first row. Each box shows the title on two lines (a "Title · " prefix that several tasks of the plan share is dropped there, the whole title is in the tooltip and the screen-reader label), then the state, the estimate and the project, and on a third line "in ritardo", "stesso repo di un task in corso" or "tocca a te" when they apply; waiting is a dashed box, an error a red box with the word "errore". A task of another goal, or of no goal, that one of ours waits on, or that waits on one of ours, shows as a dotted "ghost" box labelled "altro obiettivo" or "senza obiettivo", in the row above its waiter or below its blocker; a ghost is not expanded further, and pressing it opens its goal's graph, or its task in its node when it has no goal. A cycle never breaks the layout: what it leaves unordered goes in a last row, "fuori ordine: dipendenze in ciclo", in red. Done tasks are hidden, their links being met: "Mostra fatti (n)" in the header shows them, faded, and the rows are computed again with them. Clicking a box, or Enter or Space, selects that task in the goal's panel (state buttons, "Avvia") and highlights it with its blockers and the tasks it unblocks. Every box is reachable with Tab, row by row, and its label says its state, project, step and "aspetta: …" / "sblocca: …". "Mappa" in the header, Esc, or clicking the goal box on top leaves the graph and gives the map back with its view and zoom; a refresh keeps the graph and the selection while the goal still exists. A long graph scrolls inside the map. Below 760 px there is no graph: the list groups the goal's tasks by the same steps.

**Harness from the map.** With the harness switched on in `config.json` (`moduli.harness.attivo`), every project with a repo shows where it stands: `da decidere`, `escluso`, `da valutare`, `da rifare`, `da adeguare` or `conforme`, with the numbers and the date of the last report. Two buttons write the decision in the project's `STATE.md`: "Adegua all'harness" and "Non adeguare questo progetto". The first only records the decision and tells you the command to run in the repo (`/ai-native-harness:audit`); nothing is launched from the dashboard, because an audit runs the project's own checks. Projects with a repo and no decision stay listed under "Harness da decidere", and their node has a dashed outline, until you answer: a silence is not a no. "Nuovo progetto" asks the same question when you give a repo, and `/nuovo-progetto` and `/adotta-repo` ask it too. With the harness off none of this appears.

**Projects from the map.** "Nuovo progetto" on the map creates `projects/<name>/STATE.md` from the template and the row in `projects/INDEX.md`, like `/nuovo-progetto`: name, and optionally the repo folder, the stack and the priority. With a project selected, three buttons set its priority (alta, media, bassa) in the index row. Neither touches work projects or the confidential folder. A project whose STATE names no folder (no `Repo` line, or only `nessuno` or the template's placeholder) has "Imposta cartella" at the bottom of its panel: you type the absolute path of a git repo on this computer, and it is checked like the repo of a new project (network paths are refused before the disk is touched, and so are the work and confidential folders, a disk root, a folder that holds one of them and anything inside the vault's `projects/`). The STATE gets `- **Repo:** <path>` in place of the empty line, with today's date, and so does the date of its index row; "Avvia" then opens there. An error says what is wrong and never repeats the path. With the harness module on, the project then waits under "Harness da decidere". To change a repo that is already set, edit its STATE. "Archivia progetto", at the bottom of a project's panel, archives it after a dialog that names it and says what happens: its row leaves `projects/INDEX.md` and its folder moves to `projects/_archivio/<name>` (`<name>-YYYY-MM-DD`, then `-YYYY-MM-DD-2`…, if that is taken: nothing is ever overwritten). It is a rename inside `projects/`: no repo on disk is touched, a project folder (or `projects/_archivio`) that is a link or junction is refused, and so is one that is, holds or sits inside the confidential folder (or where it leads, if it is a link), and with `config.json` unreadable nothing moves. Its `#<name>` lines stay in `docs/piano.md` and show up again as a topic node, where "Avvia" opens the vault. To restore it, move the folder back to `projects/<name>` and put its row back in `projects/INDEX.md` (the date at the end of the row must match the `Aggiornato` line of its STATE), then run `scripts/verify`.

**Tray icon** (`second-brain.tray`, Windows and macOS, starts at login): a dot in the notification area (Windows) or the menu bar (macOS), green when the dashboard answers and red when it does not (checked every 30 seconds). Its menu has three parts. **Dashboard**: open it, start or restart it (on Windows a `server.py` of this vault still listening on port 8765 is stopped first; another program on that port is never stopped, and a notification names it), stop it (on Windows the 10-minute check starts it again; on macOS it stays stopped until you start it or log in again). **Avvia job**: start `morning`, `feed + radar` (radar starts when feed has ended), `chiusura`, `bozze` or `pulizia` now; a job that is not registered is not listed. **Notifiche**: a notification when the dashboard goes down or comes back and when a job ends with an error (once per run), with a switch that turns them off until you close the tray. **Esci** closes only the icon. Native code only: `scripts/tray/tray.ps1` (Windows PowerShell 5.1 and Windows Forms) and `scripts/tray/SecondBrainTray.swift` (AppKit; `install_jobs.py` compiles it with `swiftc` into `~/Library/Application Support/second-brain/`, which needs the Xcode Command Line Tools). `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/tray/tray.ps1 -SelfTest` prints the dashboard check, the menu and the exact command of each item without showing anything. The macOS version has not been compiled or run yet. On Windows the icon first appears at the next login; to see it now: `schtasks /run /tn second-brain.tray`.

## When a page is empty

A new install starts with empty pages on purpose: they fill when something has run once. Nothing is broken if you see these.

| Page | Fills when | What to do |
|---|---|---|
| Radar | the radar has run once | put your feeds in `memory/feeds.md`, then run `python3 scripts/feed.py` and `python3 scripts/radar.py` (Windows: `py -3`), or press Radar in the Avvii page. After that the jobs run every Monday. |
| Local model | Ollama is running and a model is downloaded | start the Ollama app (or `ollama serve`), then `ollama pull <model>`; the call list fills as the radar and the assistant use it. Swap and the process list exist only on macOS. |
| Uso di Claude | Claude Code has saved your usage percentages, and you have used it | add the status line below to `~/.claude/settings.json`; the tokens per day come from your own Claude Code sessions and appear by themselves. |
| Today, calendar part | a calendar provider is connected | see "The assistant and your calendar". |
| Avvii | the jobs are registered | `install_jobs.py`; the job status (running, loaded) is read from launchd, so only macOS shows it. |

The status line for the Claude usage page (put the real path of your vault; on Windows use `py -3 -I C:\path\to\vault\scripts\statusline-uso.py`):

```json
{ "statusLine": { "type": "command", "command": "python3 -I /path/to/vault/scripts/statusline-uso.py" } }
```

It only saves the two usage percentages and their renewal time, not the content of your sessions. It touches your global `~/.claude`, so the wizard does not do it for you.

## Commands

Start `claude` in the vault folder and type:

| Command | What it does |
|---|---|
| `/nuovo-progetto <name> [path]` | creates the project folder, its `STATE.md` and the row in `projects/INDEX.md`; with a path it also writes the `Repo:` field (one line per repo for a multi-repo project) |
| `/morning` | the morning brief: projects, news, priorities |
| `/chiudi-giornata` | rewrites the STATE files from your commits, runs the checks and commits locally; never pushes |
| `/weekly-review` | what moved, what is stuck, what is neglected |
| `/cattura <text>` | sorts what you say into the plan, areas, decisions and facts to consolidate; it writes task links (`id:`, `dopo:`, `chi:te`) only when you state them, in a commit of their own, and asks about inferred ones; `/weekly-review` moves the facts into `memory/` after one yes |
| `/post` | turns a note into a LinkedIn draft in `content/linkedin/` |
| `/bozze-settimana` | three post drafts for the week (LinkedIn and Instagram, as you chose) |
| `/commit-push-pr` | commit, push and open a PR for a code repo, asking you before the push |
| `/adotta-repo` | once: lists the git repos on your computer that the vault does not know and records your answers |
| `/kit [name]` | installs the plugins and skills listed in `kit/<name>.md` (default `lavoro`) for your user, one at a time, after `scan-before-install` (needs `uv tool install skillspector`) and your yes; with the work kit it first asks whether your company's rule allows it |

Subagents: `researcher` (reads the news and writes cards in `radar/`), `reviewer` (reviews the week, writes nothing), `writer` (drafts, only with `/post`). None of them can start another.

**Register an approved plan.** `python3 scripts/registra-piano.py <plan.md> --tag <project> --obiettivo <slug> [--titolo T] [--scadenza YYYY-MM-DD] [--giorni lun,mar,...|tutti] [--piano-rel <path>] [--senza-commit]` writes a plan made with superpowers:writing-plans into the vault, from any folder. The vault is always the one the script lives in: there is no `--vault`. The plan file must live in one of the project's repos (the `Repo:` lines of its STATE), never under the vault's `projects/`, the work folder or the confidential folder (wherever it is, and where it leads if it is a link), not even through a link, nor under the work folder, `_private` or the confidential folder name of `projects/` of another checkout of a vault. Its path relative to that repo's root becomes the goal's `piano:` and is always written; `--piano-rel` is optional and, if you pass it, must be that same path. Each `### Task <N>: <title>` becomes `- [ ] #<project> <plan title> · Task <N>: <title> id:<slug>-t<N> [dopo:...] obiettivo:<slug> [stima:...] [repo:...]` in the "Prossimi giorni" section of `docs/piano.md`, after the project's last open task there, or at the end of the section (created if missing). Inside a task the script reads only `**Dipende da:** Task 1, Task 3` (or `nessuna`), `**Stima:** 3h` or `1g` and `**Repo:** <name>`; code blocks are skipped, and a heading like `### Task 2 - B` that is not `### Task <N>: <title>` is a problem. The goal line in `docs/obiettivi.md` gets the title, `scadenza:`, `giorni:` and `piano:`; a value you do not pass stays as it was, and a new goal takes the plan title. A goal belongs to one plan file, its `piano:`: run it again on the same file and it updates the lines with the same `id:` where they are (text and markers; the checkbox and a date written in front stay) without adding duplicates. An existing `piano:` is never changed: another plan file stops, and so does a plan whose ids are already in `docs/piano.md` when the goal has no `piano:` yet. Use another `--obiettivo` for another plan. A task gone from the plan is a warning. The plan is untrusted input: only a `.md` file up to 1 MB, at most 100 tasks, and the text written follows the rules of the map's "new task" (at most 200 characters, no `<` or `>`, no control or direction characters, no word that would read as a marker), plus no `[[`, `]]`, `|`, Markdown links, images or URLs (`](`, `![`, `://`); a `#` in a title is dropped, so a plan cannot add a hashtag. The project must be in `projects/INDEX.md`, not a work project and not the confidential folder; `**Repo:**` names must be repos of that project. On any problem it writes nothing, prints one line per problem with the plan line and what to fix, and exits with 2; a task without `Dipende da` or `Stima` is a warning. It exits with 1, naming the file, when `config.json` cannot be read (it could hide the confidential folder, so the script refuses), when `docs/piano.md` or `docs/obiettivi.md` is not valid UTF-8 or cannot be written, or when the commit fails. Then it commits only `docs/piano.md` and `docs/obiettivi.md` (`docs(piano): register plan <slug>`, with the ids and links in the body), with git run without the caller's `GIT_*` variables; `--senza-commit` skips that. The registered titles enter the vault's git history: never put personal data in a plan's titles. The script and the dashboard do not lock against each other: do not tick or add tasks in the dashboard while a plan is being registered. No network.

Your skills follow your projects. The *Stack* column of `projects/INDEX.md` is compared with the *Skills* line of `memory/about-me.md`: `/nuovo-progetto` asks for the stack and proposes the technologies you do not list yet; `/chiudi-giornata` does the same with you in front of it, and in the unattended run it only writes one line per missing technology in *Da confermare* of today's `daily/` (for example: ``Aggiungere `Postgres` alle competenze in memory/about-me.md (da progetto api-ordini)``). `memory/about-me.md` changes only after your yes, one item at a time. The confidential folder is not in the index, so it is never read for this. A technology you decline comes back on the next day with activity: there is no list of declined items yet.

## Scheduled jobs

`scripts/jobs.json` defines the jobs once; `python3 install_jobs.py` registers them with the scheduler of your system: launchd on macOS, systemd user timers on Linux, Task Scheduler on Windows. Start with `python3 install_jobs.py --dry-run` to read what it would do. `python3 install_jobs.py --uninstall` removes them. Each job is safe to start twice, so catching up after the computer was off is harmless. The jobs of a module you chose are registered; the other optional ones need `--all`.

| Job | When | What it does |
|---|---|---|
| `second-brain.morning` | weekdays 08:00 and at login (macOS and Windows; not on Linux yet) | the morning start: closes pending work, creates the daily note |
| `second-brain.chiusura` | weekdays 18:30 | `/chiudi-giornata`: rewrites the STATE files from your commits |
| `second-brain.pulizia` | Friday 18:00 | weekly check and report |
| `second-brain.dashboard` | at login, kept running | the local dashboard |
| `second-brain.feed` (optional, chosen in setup) | Monday 07:00 | `scripts/feed.py`: collects the news from `memory/feeds.md` into `inbox/` (built-in collector; skip it if you use n8n) |
| `second-brain.radar` (optional, chosen in setup) | Monday 07:30 | filters the news in `inbox/` for your projects, with the models you chose |
| `second-brain.bozze` (optional, chosen in setup) | Monday 08:30 | `/bozze-settimana`: three post drafts |
| `second-brain.tray` | at login (macOS and Windows) | the tray or menu-bar icon (see "The dashboard"); "Esci" closes it until the next login |

The text of a news item is untrusted: every title goes through `content-guard` (hidden-instruction patterns) before any model sees it. Logs are in `~/Library/Logs` (macOS), `$XDG_STATE_HOME/second-brain` or `~/.local/state/second-brain` (Linux), `%LOCALAPPDATA%\second-brain\logs` (Windows).

## Checks

- `python3 scripts/check` is the single check to run before a commit or a pull request: `scripts/verify`, the linter ([ruff](https://docs.astral.sh/ruff/), rules in `ruff.toml`), the script tests, the template tests and a gitleaks scan of the git history, like the CI job (files git ignores are not scanned; findings show file and line, never the secret). It stops at the first red step and says which one. It needs ruff and gitleaks: `doctor.py` lists them as optional and prints the install command, with the ruff version CI uses.
- `python3 scripts/verify` checks the vault rules: short STATE files, a consistent `INDEX`, a valid `Harness` line where there is one, valid links, that this README mentions every job and command, and the `scaffold/` registry if you have one. Broken dependencies in `docs/piano.md` (a duplicate `id:`, a `dopo:` that points nowhere, a cycle), an `obiettivo:` that `docs/obiettivi.md` does not define, a `repo:<name>[,<name>…]` on a task with no project `#tag` or naming something that is not a repo of that project (the short name is the folder name of a `Repo` line of its `STATE.md`) and the invalid lines of that file are warnings, printed as `docs/piano.md:<line>: avviso: ...` (`docs/obiettivi.md:<line>: avviso: ...` for the lines of that file): they never block it or change its exit code. `docs/obiettivi.md` lists the goals the `obiettivo:<slug>` markers of the plan point to, one per line as `- slug: titolo` (title up to 120 characters; other lines are ignored). A goal line can end with markers, read from the end like the task markers (the scan stops at the first invalid or repeated one): `scadenza:YYYY-MM-DD` (the deadline), `giorni:` with a comma list of `lun,mar,mer,gio,ven,sab,dom` or `giorni:tutti` (the goal's working days; without it the vault calendar applies) and `piano:<path>` (the plan file, relative to the repo root: letters, digits, `.`, `_`, `-` and `/`, at most 200 characters, no spaces, no `..`, not absolute), as in `- rilascio: Rilascio 1.0 scadenza:2026-12-04 giorni:lun,mar,mer piano:docs/piano.md`. A task's estimate is its `stima:<n>h` or `stima:<n>g` marker (`9h`, `1,5g`), and a day is `ore_giorno` hours. The vault calendar is set in `config.json` as `"piano": {"ore_giorno": 6, "giorni_lavoro": ["lun", "mar", "mer", "gio", "ven"]}`, which are also the defaults; `ore_giorno` goes from 1 to 24. For a goal with a deadline the due dates of its open tasks are computed, never written in the plan: a task is due by the deadline minus the working days its open successors in the same goal still need (the longest chain of their estimates), a task without an estimate counts zero hours, and independent tasks are assumed to proceed in parallel. An invalid goal marker or `piano` setting is a warning too (`docs/obiettivi.md:<line>: avviso: ...`, `config.json: avviso: ...`): the goal stays defined, an invalid `giorni:` falls back to the vault calendar and an invalid setting to its default. A repo whose folder name cannot be written as a `repo:` marker (over 60 characters, or characters other than letters, digits, `.`, `_` and `-`) is a warning on its STATE (`projects/<project>/STATE.md: avviso: repo:<name> non si può scrivere come marcatore: rinomina la cartella`): the dashboard lists it, but no task can name it with `repo:`. Two `Repo` lines of the same project with the same folder name are an error that does block it, because the name is what a `repo:` is checked against. `projects/_archivio/` holds the projects archived from the dashboard: it is not checked against `INDEX`, and a link written when a project was still in `projects/<name>/` (in a daily note, say) stays valid once it is archived. Run it after any change to a STATE or the index; `/chiudi-giornata` runs it for you.
- `python3 doctor.py` checks Python, git, Claude Code, `verify`, and what your choices need (Ollama running, each local model downloaded, enough RAM, n8n if you picked it). `--ci` checks only the required items.
- Secret scan: `scripts/hooks/pre-commit` runs gitleaks on what you are about to commit and blocks the commit if it finds a secret. Turn it on once per clone with `git config core.hooksPath scripts/hooks`; it needs [gitleaks](https://github.com/gitleaks/gitleaks) installed (`doctor.py` shows how). `doctor.py` also tells you when the hook is not switched on in this clone: a new clone or worktree commits without these checks until you run that command. It also tells you when the status line in `~/.claude/settings.json` runs a Python or a `statusline-uso.py` that is no longer there (a folder renamed or deleted): Claude Code shows no error, the usage page just stays on old numbers. It prints the `statusLine` to paste.

## Track the repos you already have

The `scaffold` module is optional. It creates `scaffold/registro.md` (the project templates you start from, empty), `scaffold/profili/personal.md` and `scaffold/profili/lavoro.md` (what to do for your own projects and for work ones; work has no AI features and no remote repo), `scaffold/ignorati.md` (repos you said "ignore" or "not now" to) and `scaffold/hook-avvio.md`.

- `/adotta-repo` asks where to look, lists the git repos the vault does not know (repos with the same remote are grouped) and records your answer for each: track it, ignore it, ask again in 7 days, or "work". For a work repo only a hash of the path is saved, never the path or the name.
- `scripts/blocchi-regole.py` counts how many times each rule of the hook refused a command or asked for confirmation (`--giorni N`, default 7; `--json`). The hook writes one line per block to `second-brain-regole.log` in the log folder: the date, the name of the rule and the action, never the command or a path. The evening close passes today's counts to `/chiudi-giornata`; `/weekly-review` uses the week's counts to ask which blocks were false positives. `git config core.hooksPath` without a value only reads the setting and is no longer refused.
- `scripts/harness-progetti.py` tells where each project stands with the agent harness (the checks and guardrails that let an agent work safely in a repo). The decision is an optional line in the project's `STATE.md`: `- **Harness:** da decidere`, `adeguare (date)` or `non adeguare questo progetto (date)`. A refusal counts only when written out in full; a missing line means "not decided yet". The state comes from `.claude/harness-status.json` in the project repo, the summary an audit leaves there: the script reads four numbers and a date from it, nothing else, and a file that does not add up counts as "to be assessed". It never writes, runs nothing from the repo, skips the work and confidential folders in any case and never touches a repo on a network path; when `config.json` cannot be read or has an unexpected shape it reads no repo, says so on stderr and exits with 1. `scripts/attivita-progetti.py` (the project activity read by the morning and evening routines) follows the same rules: no reserved STATE is read, a network repo is skipped before git runs, and an unreadable `config.json` prints nothing and exits with 1. `--json` prints a list.
- `scripts/repo-non-tracciato.py` tells whether the current folder is an untracked git repo. It never writes by itself. With the hook in `scaffold/hook-avvio.md` Claude Code can remind you when you open such a repo. That hook touches your global `~/.claude` settings, so the wizard does **not** install it: the file shows the two lines to paste, and you decide.
- A repo is "tracked" when its path is in a `Repo:` line of a `projects/*/STATE.md`.
- One project can span several repos (for example a backend, an app and a frontend): write one `- **Repo:** <path>` line per repo, one under the other, one absolute path per line. `/chiudi-giornata`, the morning start, `/weekly-review` and the dashboard read the commits of all of them, and none of them shows up as untracked. In `/adotta-repo` a "yes" can add the repo to an existing project instead of creating a new one.

  ```markdown
  - **Repo:** /srv/code/shop/backend
  - **Repo:** /srv/code/shop/app
  - **Repo:** /srv/code/shop/frontend
  ```

## Privacy

Claude Code sends the files it reads to the model. Put confidential notes in the folder the `riservata` module made (ignored by git and blocked by `deny` rules) and read [ADR-002](docs/adr/ADR-002-confidential-notes.md) for the limits of that block: the rules do not stop a script you run yourself. `scripts/elabora-richieste.py`, which turns the dashboard's post requests into drafts with `claude -p`, skips the work and confidential folders; when `config.json` exists but cannot be read it processes nothing and its run counts as failed, because the confidential folder is then unknown. Your name, notes and memory files stay in your copy: `setup.py` writes them from the `*.example.md` files and git ignores them. Calendar addresses and passwords stay outside the vault. The dashboard listens only on `127.0.0.1`. Its pages never show the raw text of an error: only known codes and fixed sentences reach them. A calendar that cannot be read gives a fixed reason in Agenda (for example "manca il file dei calendari (vedi la guida)" or "il file dei calendari è leggibile da altri utenti: chmod 600 (vedi la guida)") instead of naming the file or the calendars, and the dashboard's own log gets only the error class and that reason's id; a model that does not answer says to check `modelli.assistente` in `config.json`. The rule for the confidential folder comes from `moduli.py` at the vault root: if that file is missing, launches and the scripts that read projects refuse, and the scripts say that `moduli.py` is missing. **Residual risks** of the confidential-folder checks: a local link or junction that leads to a network share is followed when the path is resolved, before the resolved path is checked; on macOS and Linux a mounted network share looks like a local folder (only `//server` paths and, on Windows, `\\server` paths and mapped drive letters are recognised); a hard link to a confidential file cannot be told apart from the file itself. The Obsidian Sync core plugin is off in `.obsidian/`: turning it on would also sync the git-ignored confidential folder.

## Troubleshooting

- **`python3` not found on Windows**: use `py -3`.
- **Certificate error when fetching feeds on macOS**: the Python from python.org has no certificate store; the collector falls back to the system one. If it still fails, run `Install Certificates.command` from the Python folder in Applications.
- **`doctor.py` says Ollama is missing or not running**: start the Ollama app, or choose `none` for that step with `python3 setup.py --add radar`.
- **A model is missing**: `ollama pull <model>` (the name is in the `doctor.py` message).
- **The assistant says it does not know your appointments**: no calendar is connected, the calendar cannot be read, or the model is `claude` and you did not allow sending appointments. `config.json` shows `calendario.provider` and `moduli.assistente`.
- **"è leggibile da altri utenti" (the message is in Italian in v0.1)**: `chmod 600` on that file.
- **On Windows, `./scripts/verify` does not start inside Claude Code** (Git Bash cannot run the `python3` shebang): use `py -3 scripts/verify`. The commands and the permissions already allow it.
- **On Windows the jobs run without a window**: Task Scheduler starts them through `conhost.exe --headless`, so no empty CMD window appears. If a job registered before this change still opens one, run `py -3 install_jobs.py` again to re-register it.
- **Why the tray job uses `-ExecutionPolicy Bypass`**: the default Windows policy (Restricted) blocks every script, including `tray.ps1`. The bypass applies only to that one PowerShell process and only to that one file of this repo; it does not change your system policy. Signing the script would avoid it, but is out of scope for now. If your organisation forbids it, uninstall only this job: `py -3 install_jobs.py --uninstall --only tray`.
- **`scripts/verify` complains**: the message names the file and line; fix that and run it again.
- **Jobs do not run on Linux when you are logged out**: `loginctl enable-linger $USER`.

## Update and uninstall

Update: `git pull`, then `python3 doctor.py` and `python3 scripts/verify`. Your files are ignored by git or untouched by the pull. Uninstall: `python3 install_jobs.py --uninstall`, then delete the folder. On macOS also delete `~/Library/Application Support/second-brain/` (the compiled tray icon). Claude Code and Ollama have their own uninstall guides.
